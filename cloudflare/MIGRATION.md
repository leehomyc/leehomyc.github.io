The production project is now connected to GitHub `leehomyc/leehomyc.github.io`, branch `master`, with automatic deployments enabled, build command `node cloudflare/prepare-pages.mjs`, output `cloudflare/dist`.

Only requests Cloudflare identifies as `CN` register `cn-connection-sw.js`, which relays the fixed Firebase SDK, Auth and Firestore endpoints through `/api/cn-proxy/*`. All players keep the same Firebase project, saves and leaderboards. Other regions use the existing direct connection. The browser unregisters the mainland service worker after a region change. Google OAuth still depends on Google's sign-in page and requires separate verification from a mainland network.

## Deployment sequence

1. Sign in to the intended Cloudflare account in the existing Chrome session.
2. Create a Pages project named spell-legion if that name is free in the account, deploy dist/, and verify game load, saves, email/Google auth and two-client rooms on the returned pages.dev URL.
3. Add the deployed hostname to Firebase Authentication authorized domains during the transition. Verify popup sign-in on the new origin.
4. Register/confirm ownership of spelllegion.com, review existing DNS before any nameserver change, attach domain in Pages and verify TLS. Update invite links and authorized domains.
5. Build and deploy a separate Worker exporting the Durable Object class; Pages cannot itself define a Durable Object. Establish versioned client/server protocol before replacing the existing link transport.
6. Move authoritative movement, cooldowns, damage, shared loot, progression and settlement into the room simulation. Reuse client prediction for presentation only. Do not accept final rank or damage claims from clients as authoritative.
7. Add D1-backed saves and verified match results. Keep a stable mapping from existing Firebase UID to migrated identity. Preserve Firebase Authentication initially; replacing authentication requires an explicit session, password/identity migration and email delivery design.
8. Export and reconcile Firestore collections before switching writes. Include anonymous users and Google-linked accounts. Require record counts, sample comparisons and rollback verification before switching production reads.
9. Switch writes once to the new backend; avoid naively dual-writing mutable gold or progression. Verify new saves, login recovery and ranked results before retiring Firebase.

## Performance and cost gates

- A Durable Object room has one placement. Region hints are best-effort, not guaranteed Hong Kong placement. Measure from Hong Kong and representative overseas locations.
- Object count does not establish simulation capacity or cost. Benchmark real enemy counts and snapshot sizes at 2/4 players before setting room limits.
- Continuous 15–20 Hz simulation cannot sleep like an idle WebSocket room. Measure active duration, CPU, fan-out bandwidth and storage operations.
- Do not write every tick to D1 or KV. Keep battle state in the room; persist bounded checkpoints and final verified settlements. KV is not an authoritative balance store.
- Start with capped test traffic. 50,000 concurrent rooms is a load-testing target, not a verified capacity claim.
- Disconnect, reconnect, duplicate inputs and settlement idempotency must pass before ranked trophy changes are enabled.

## Rollback

Keep hyang.org/spell-legion and Firebase untouched until the Cloudflare path passes verification. Keep the old source revision and data exports. Retain existing DNS values before cutover. Never reset browser saves as part of origin migration; localStorage is origin-specific and needs an authenticated cloud transfer or an explicit export/import path.
